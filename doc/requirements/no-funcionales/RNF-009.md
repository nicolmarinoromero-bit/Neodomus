# RNF-009 — Escalabilidad horizontal

- **Identificación:**

| Campo | Valor |
|---|---|
| ID | RNF-009 |
| Nombre | Escalabilidad horizontal |
| Categoría | Arquitectura |
| Prioridad | Media |
| Estado | Implementado |
| Fecha | Mayo 2026 |

- **Descripción:**  
  La arquitectura debe permitir la integración futura de nuevos módulos (por ejemplo, monitoreo IoT o control por voz) sin rediseñar el sistema completo.

- **Criterio:**  
  - Añadir un módulo nuevo (registro, endpoint, pantalla) sin modificar los módulos existentes.
  - Es posible escalar instancias del backend con balanceo de carga si se requiere.

- **Implementación actual:**  
  - **Arquitectura modular y desacoplada por dominios:** cada funcionalidad vive en su propio router (auth, citas, tecnicos, productos, consultas, reports, solicitudes, users, clientes) y su propio conjunto de modelos/esquemas/servicios; incorporar un nuevo módulo (p. ej. IoT o voz) implica agregar un router y sus modelos sin tocar los existentes.
  - El backend es una API stateless (FastAPI con tokens JWT), condición necesaria para replicar instancias detrás de un balanceador.
  - Despliegue por contenedores (`docker-compose`): cada servicio (api, frontend, db) es independiente y puede escalarse con `docker-compose up --scale api=N`.
  - La app móvil (`movil/`) ya esboza la intención futura de módulos IoT (servicios `dispositivos.service.ts` con encender/apagar), aunque el backend aún no los implementa.
  - Las interfaces externas (SMTP) están aisladas en `be/app/utils/email.py`, facilitando el cambio de proveedor.

- **Evidencia técnica:**  
  - `be/app/main.py` → registro de routers por dominio
  - `be/app/routers/`, `be/app/models/`, `be/app/schemas/` → módulos independientes
  - `docker-compose.yml` → servicios independientes y escalables
  - `movil/services/dispositivos.service.ts` → esqueleto de integración IoT
  - `doc/requirements/non-functional.md` → RNF-07.1 a RNF-07.4

- **Validación:**  
  - Añadir un router de prueba y verificar que se integra sin cambios en los demás.
  - Ejecutar múltiples instancias de `api` detrás de un balanceador y verificar sesiones (los tokens JWT no guardan estado).
  - Revisar que no hay acoplamiento cruzado entre routers (solo dependencias compartidas en `utils`/`services`).

- **Observaciones:**  
  - La arquitectura cumple el criterio; los módulos futuros de monitoreo IoT/control por voz están contemplados en la documentación (RF-FUT-01/02) y esbozados en `movil/`, pero pendientes de desarrollo.

# RNF-001 — Seguridad

- **Identificación:**

| Campo | Valor |
|---|---|
| ID | RNF-001 |
| Nombre | Seguridad |
| Categoría | Seguridad |
| Prioridad | Alta |
| Estado | Parcialmente implementado |
| Fecha | Mayo 2026 |

- **Descripción:**  
  El sistema debe proteger la información de los usuarios mediante cifrado de contraseñas y conexiones seguras, y debe diferenciar el acceso por roles (usuario, técnico y administrador).

- **Criterio:**  
  - Las contraseñas no deben almacenarse en texto plano ni con hashes débiles.
  - Las comunicaciones entre cliente y servidor deben ir cifradas (HTTPS/TLS) en producción.
  - Los roles deben tener permisos diferenciados y verificables en cada operación.

- **Implementación actual:**  
  - Las contraseñas se cifran con **bcrypt de 12 rondas** (`passlib`/`bcrypt` en `be/app/utils/security.py`, `hash_password`), no con SHA-256 ni MD5 (las restricciones del proyecto RC-04.2 exigen bcrypt).
  - Los tokens JWT se firman con **HS256** (algoritmo basado en SHA-256) usando `SECRET_KEY` del entorno; access token de 15 min y refresh token de 7 días según `.env`.
  - Acceso diferenciado por rol: dependencias `get_current_client`, `get_current_employee` y helpers `_admin` (acepta `admin`/`administrador`) en los routers, más el decorador `require_roles`; los tokens incluyen `user_type` y `rol`.
  - En desarrollo la API corre en HTTP local (`http://localhost:8000`); el despliegue en producción debe configurar TLS/HTTPS.
  - Rate limiting instalado (`slowapi`) pero **no aplicado a ningún endpoint**; no hay bloqueo por IP tras intentos fallidos (RC-04.4 pendiente).

- **Evidencia técnica:**  
  - `be/app/utils/security.py` → `hash_password`, `verify_password`, `create_access_token`, `create_refresh_token`, `require_roles`
  - `be/app/dependencies.py` → `get_current_user`, `get_current_employee`, `get_current_client`, `OAuth2PasswordBearer`
  - `be/app/middleware/cors.py`, `be/app/middleware/rate_limit.py`, `be/app/utils/limiter.py`
  - `be/app/config.py` → `SECRET_KEY`, `ALGORITHM`, tiempos de expiración
  - `fe/src/services/api.ts` → encabezado `Authorization: Bearer`
  - `doc/requirements/constraints.md` → RC-04

- **Validación:**  
  - Verificar en la base de datos que `password_hash` no contiene contraseñas en texto plano y que todas las cuentas usan `$2b$12$...`.
  - Intentar acceder a un endpoint de administración con un token de cliente (debe responder 403).
  - Revisar `pyJWT`/`python-jose` y comprobar la firma y expiración de los tokens.
  - En producción, comprobar que todo el tráfico usa HTTPS (certificado TLS válido).

- **Observaciones:**  
  - El requisito menciona cifrado SHA-256 para la información; el proyecto implementa bcrypt para contraseñas (más robusto) y HS256 para JWT, en línea con la documentación interna (RC-04).
  - HTTPS solo en despliegue; el desarrollo es local/HTTP.
  - Existe una incoherencia conocida: `GET /users/` exige `require_roles("admin")` mientras el rol sembrado es `"administrador"` (validación exacta), lo que provoca 403 aunque el helper `_admin` acepte ambos.
  - Faltan: rate limiting efectivo, bloqueo por IP tras 5 intentos fallidos en 15 minutos y auditoría de dependencias (CVE).

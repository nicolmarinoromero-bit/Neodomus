# RNF-008 — Eficiencia de desempeño de la base de datos

- **Identificación:**

| Campo | Valor |
|---|---|
| ID | RNF-008 |
| Nombre | Eficiencia de desempeño de la base de datos |
| Categoría | Rendimiento / Datos |
| Prioridad | Media |
| Estado | Parcialmente implementado |
| Fecha | Mayo 2026 |

- **Descripción:**  
  La base de datos debe optimizar las consultas para reducir el tiempo de carga en cada módulo.

- **Criterio:**  
  - Índices sobre las columnas de búsqueda frecuente (correo, documento, estado, claves foráneas).
  - Consultas eficientes en los módulos de mayor uso (catálogo, autenticación, citas, reportes).
  - Las tablas deben soportar transacciones ACID (InnoDB) y estar normalizadas.

- **Implementación actual:**  
  - **Índices presentes en columnas clave:** `email` (índice + unique) en `clientes`, `usuarios` y `pending_registrations`; `documento_cliente`/`documento_usuario` (únicos); `email` y `token` en `password_reset_tokens`; `id_cliente` con `index=True` en `citas` y `solicitudes_cuenta`; referencias únicas en `productos.referencia_producto` y `proveedores.correo_proveedor`.
  - Motor **InnoDB** (MySQL por defecto en la migración inicial), que soporta transacciones ACID y claves foráneas.
  - Catálogo paginado (`page`/`limit`) para limitar las respuestas grandes.
  - Normalización razonable del esquema (separación de clientes, usuarios, productos, variantes, categorías, pedidos, citas, etc.).
  - **Limitaciones:** los estados de `citas` y `pedidos` se guardan como cadenas (`String`) sin tipo ENUM; no hay mediciones de tiempos de consulta registradas; `detalle_pedido` referencia `id_servicio_d` y `id_comision_d` sin claves foráneas reales.

- **Evidencia técnica:**  
  - `be/app/models/cliente.py`, `user.py`, `cita.py`, `solicitud_cuenta.py`, `producto.py`, `password_reset_token.py` (índices y unicidad)
  - `be/alembic/versions/0001_baseline_esquema_inicial.py` (InnoDB/MySQL 8)
  - `be/app/routers/productos.py` (paginación)
  - `doc/requirements/non-functional.md` → RNF-09

- **Validación:**  
  - Ejecutar `EXPLAIN` sobre las consultas de login, catálogo y citas y verificar el uso de índices.
  - Medir tiempos de respuesta de los endpoints principales con conjuntos de datos grandes.
  - Verificar con `SHOW CREATE TABLE` que las tablas usan InnoDB.

- **Observaciones:**  
  - Los índices esenciales existen y el esquema está normalizado, pero faltan: estado como ENUM en `estados_cita`/`estado_pedido`, mediciones de rendimiento y triggers/procedimientos documentados en RC-08 (RC-08.4, RC-08.5, RC-08.6 sin implementar).

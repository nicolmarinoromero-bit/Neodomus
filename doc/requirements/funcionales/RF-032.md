# RF-032 — Reactivación de usuarios o técnicos suspendidos (administrador)

- **Identificación:**

| Campo | Valor |
|---|---|
| ID | RF-032 |
| Nombre | Reactivación de usuarios o técnicos suspendidos |
| Módulo | Administración / Gestión de personal |
| Prioridad | Alta |
| Estado | Implementado |
| Fecha | Mayo 2026 |

- **Descripción:**  
  Permite al administrador reactivar las cuentas suspendidas. Neodomus lo implementa de dos formas: (1) para **empleados** (técnicos), la edición del usuario con `PUT /api/v1/users/{user_id}` incluye el campo `is_active`, que el administrador puede volver a `true` desde `AdminTecnicos.tsx`; (2) para **clientes**, el flujo de solicitudes de cuenta: el cliente solicita su habilitación (`POST /api/v1/clients/me/cuenta-solicitud` con tipo `habilitar`, o `POST /api/v1/auth/solicitar-habilitacion` desde el login) y el administrador aprueba la solicitud en `AdminDashboard.tsx`, lo que restablece `is_active=True`.

- **Entradas:**
  - ID del usuario (`user_id`) con `is_active: true` (caso empleado).
  - O bien: aprobación de una solicitud de cuenta de tipo `habilitar` (caso cliente).
  - Token JWT de administrador.

- **Proceso:**
  i. Empleados: el administrador edita al técnico en `AdminTecnicos.tsx` y activa la casilla de estado; el frontend envía `PUT /api/v1/users/{user_id}` con `is_active: true`.
  ii. Clientes: el cliente con cuenta inhabilitada solicita la habilitación desde el login (flujo `solicitar-habilitacion`); la solicitud queda `pendiente` en `solicitudes_cuenta`.
  iii. El administrador ve las solicitudes en `AdminDashboard.tsx` (`GET /api/v1/admin/account-requests`) y aprueba la de tipo `habilitar` (`PUT /api/v1/admin/account-requests/{id}/aprobar`).
  iv. El backend marca la solicitud aprobada y establece `cliente.is_active = True`.
  v. El cliente puede volver a iniciar sesión.

- **Salidas:**
  - Cuenta del empleado o cliente reactivada (`is_active=True`).
  - Respuesta HTTP con mensaje de confirmación.
  - Estado de la solicitud en `aprobada` con `resuelta_por`/`resuelta_at`.

- **Reglas de negocio:**
  - Una solicitud de cuenta solo puede resolverse si está `pendiente` (400 en caso contrario).
  - Solo el administrador puede aprobar o rechazar solicitudes y reactivar empleados.

- **Evidencia técnica:**
  - `be/app/routers/users.py` → `PUT /users/{user_id}` (campo `is_active`)
  - `be/app/routers/solicitudes.py` → `GET /admin/account-requests`, `PUT .../aprobar`
  - `be/app/routers/clientes.py` → `POST /clients/me/cuenta-solicitud`
  - `be/app/routers/auth.py` → `POST /auth/solicitar-habilitacion`
  - `fe/src/pages/admin/AdminTecnicos.tsx`, `fe/src/pages/admin/AdminDashboard.tsx`

# RF-003 — Inicio de sesión con nombre de usuario y contraseña

- **Identificación:**

| Campo | Valor |
|---|---|
| ID | RF-003 |
| Nombre | Inicio de sesión con nombre de usuario y contraseña |
| Módulo | Autenticación / Gestión de cuentas |
| Prioridad | Alta |
| Estado | Implementado |
| Fecha | Mayo 2026 |

- **Descripción:**  
  Permite a clientes, técnicos y administradores ingresar a la plataforma con sus credenciales. El requisito menciona "nombre de usuario", pero en Neodomus la identificación es por **correo electrónico y contraseña** (no existe campo de usuario). El endpoint unifica los tres roles: si no se indica el tipo, primero prueba contra `clientes` y luego contra `usuarios` (empleados: técnicos y administradores). Al ingresar, el sistema emite un par de tokens JWT (access y refresh).

- **Entradas:**
  - Correo electrónico (`email`).
  - Contraseña (`password`).
  - Tipo de usuario opcional (`user_type`: `"client"` o `"employee"`).

- **Proceso:**
  i. El usuario ingresa sus credenciales en `fe/src/pages/auth/Login.tsx` o en el modal de autenticación (`fe/src/components/auth/AuthModalHost.tsx`).
  ii. El frontend llama a `POST /api/v1/auth/login` con `UserLogin`.
  iii. `login` (`be/app/services/auth_service.py`) busca el cliente o el empleado por correo y verifica la contraseña con bcrypt (`verify_password`).
  iv. Valida que la cuenta esté activa (`is_active=True`); si está inactiva responde 403.
  v. Registra auditoría de éxito o de fallo (`LOGIN_SUCCESS` / `LOGIN_FAILED` en `be/app/utils/audit_log.py`), sin registrar ni bloquear por IP tras intentos fallidos.
  vi. Genera `access_token` (expira en 15 minutos según `.env`; `ACCESS_TOKEN_EXPIRE_MINUTES`) y `refresh_token` (7 días; `REFRESH_TOKEN_EXPIRE_DAYS`) con `create_access_token` / `create_refresh_token`.
  vii. El frontend guarda los tokens y el perfil en `localStorage` (`AuthContext.tsx`), obtiene el perfil (`GET /users/me` o `GET /clients/me`) y redirige según el rol (`RoleRoute.tsx`).
  viii. El interceptor de Axios (`fe/src/services/api.ts`) adjunta `Authorization: Bearer` a las peticiones y renueva la sesión automáticamente con `POST /api/v1/auth/refresh` cuando el access token expira (401).

- **Salidas:**
  - Respuesta HTTP con `{access_token, refresh_token, token_type: "bearer", user_type, rol}`.
  - Sesión activa en el cliente (tokens en localStorage).
  - Redirección al panel correspondiente: cliente, técnico o administrador.
  - Entradas de auditoría `LOGIN_SUCCESS` / `LOGIN_FAILED` en stderr.

- **Reglas de negocio:**
  - El correo y la contraseña deben corresponder a una cuenta activa.
  - Los tokens JWT se firman con HS256 y contienen `sub` (email), `user_type`, `rol` y `uid`.
  - El access token expira a los 15 minutos y el refresh token a los 7 días (configuración actual en `.env`).

- **Evidencia técnica:**
  - `be/app/routers/auth.py` → `POST /auth/login`
  - `be/app/services/auth_service.py` → `login`
  - `be/app/utils/security.py` → `create_access_token`, `create_refresh_token`, `verify_password`
  - `be/app/utils/audit_log.py` → `LOGIN_SUCCESS`, `LOGIN_FAILED`
  - `fe/src/contexts/AuthContext.tsx`, `fe/src/pages/auth/Login.tsx`, `fe/src/services/api.ts`, `fe/src/components/layout/RoleRoute.tsx`

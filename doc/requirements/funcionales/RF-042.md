# RF-042 — Gestión de roles y permisos de acceso (administrador)

- **Identificación:**

| Campo | Valor |
|---|---|
| ID | RF-042 |
| Nombre | Gestión de roles y permisos de acceso |
| Módulo | Administración / Seguridad |
| Prioridad | Alta |
| Estado | Parcialmente implementado |
| Fecha | Mayo 2026 |

- **Descripción:**  
  El requisito exige que el administrador gestione los roles y permisos de acceso del sistema. Neodomus implementa **roles predefinidos y diferenciados**: la tabla `roles_usuario` contiene los roles sembrados `administrador` (id 1) y `tecnico` (id 2), los clientes se identifican aparte (tabla `clientes`), el administrador puede consultar los roles (`GET /api/v1/users/roles`) y asignar el rol al crear empleados (`POST /api/v1/users` con `id_rol`). El control de acceso se aplica mediante dependencias (`get_current_client`, `get_current_employee`, helpers `_admin`) y decoradores (`require_roles`). Sin embargo, **no se pueden crear roles personalizados ni modificar permisos por rol**: la gestión se limita a asignar uno de los roles existentes.

- **Entradas:**
  - `id_rol` al crear un empleado.
  - Token JWT de administrador.

- **Proceso:**
  i. El administrador crea un empleado indicando el `id_rol` (1 = administrador, 2 = técnico); la ficha técnica solo se crea para el rol técnico.
  ii. El sistema valida los roles en cada operación: clientes (`get_current_client`), empleados (`get_current_employee`) y administración (helper `_admin` que acepta `admin`/`administrador`).
  iii. El rol se asigna mediante la relación `id_rol_u` en la tabla `usuarios`.
  iv. No existe interfaz para crear roles ni para configurar permisos específicos por rol.

- **Salidas:**
  - Usuarios con rol asignado; acceso restringido según el rol en cada endpoint.
  - Lista de roles disponibles (`GET /api/v1/users/roles`).

- **Reglas de negocio:**
  - Los roles disponibles son `administrador` y `tecnico`; los clientes tienen su propio tipo (`user_type: client`).
  - La creación de empleados con rol técnico genera automáticamente la ficha técnica.
  - No se implementa la creación de roles personalizados ni la edición de permisos (HU-40 parcial).

- **Evidencia técnica:**
  - `be/app/routers/users.py` → `GET /users/roles`, `POST /users` (campo `id_rol`), helper `_admin`
  - `be/app/models/roles_usuario.py`; migración `0001_baseline_esquema_inicial.py` (seed de roles)
  - `be/app/utils/security.py` → `require_roles`
  - `be/app/dependencies.py` → `get_current_employee`, `get_current_client`
  - `fe/src/pages/admin/AdminTecnicos.tsx`

- **Observación:**  
  Existe una incoherencia interna: `GET /users/` aplica `@require_roles("admin")` (comparación exacta) mientras el rol sembrado se llama `"administrador"`, lo que en la práctica rechaza la petición pese al helper `_admin` que sí acepta ambos valores.
